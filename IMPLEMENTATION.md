# GraphRAG-RL — руководство по реализации

Документ описывает метод с точки зрения кода: какие модули нужны, какие данные ходят
между ними, какие алгоритмы внутри и чем проверяется каждый этап. Числа приводятся
только там, где они являются параметром реализации (размерности, гиперпараметры,
лимиты), результаты экспериментов здесь не рассматриваются.

---

## 0. Что строится

Система отвечает на вопрос по корпусу нормативных документов и сопровождает ответ
ссылками на конкретные статьи. Ключевое отличие от обычного RAG: **отбор контекста не
задан правилом, а управляется обученной политикой**. Политика на каждом шаге решает, к
какому уровню поиска обратиться, по какой связи пройти в графе и когда остановиться.

Контур делится на две независимые части:

| Часть | Что делает | Обучается |
|---|---|---|
| **Подсистема отбора** | строит контекст: три ретривера + граф + контроллер | да, обучением с подкреплением |
| **Генератор** | формирует текст ответа по готовому контексту | нет, внешняя модель |

Разделение принципиально для кода: **генератор никогда не вызывается внутри цикла
обучения**. Награда считается по отобранным фрагментам, а не по тексту ответа. Это
позволяет обучать политику дёшево и менять генератор без переобучения.

## 2. Этап 1. Данные

### 2.1 Контракт записи документа

Всё, что делает конвейер, сводится к приведению исходного файла к этой структуре:

```json
{
  "doc_id": "LAW-547-2019",
  "meta": {
    "type": "Закон",
    "date": "2019-05-14",
    "organ": "Олий Мажлис",
    "lang": ["ru", "uz-Cyrl", "uz-Latn"],
    "status": "действующий"
  },
  "source": {
    "store": "ведомственный архив",
    "file":  "LAW-547-2019.pdf",
    "pages": "12-13"
  },
  "structure": [
    { "node_id": "LAW-547-2019/ГЛ.3",        "type": "глава",  "title": "..." },
    { "node_id": "LAW-547-2019/ГЛ.3/СТ.21",  "type": "статья", "title": "..." }
  ],
  "chunks": [
    { "chunk_id": "LAW-547-2019/СТ.21#1",
      "parent":   "LAW-547-2019/ГЛ.3/СТ.21",
      "par": 1, "tokens": 148, "src": "с. 12, абз. 1-3",
      "text": "..." }
  ]
}
```

Поле `parent` — это и есть будущее отображение `μ`: фрагмент всегда знает свою вершину.
Поле `src` нужно для прослеживаемости: ответ должен приводить не документ вообще, а
место в нём.

### 2.2 Нормализация (`normalize.py`)

Порядок операций важен, каждая следующая опирается на результат предыдущей:

1. приведение кодировок к единому виду;
2. унификация дат к ISO-формату;
3. приведение нумерации статей и пунктов к канонической форме (римские и арабские цифры,
   разные виды скобок и точек);
4. согласование кириллицы и латиницы для узбекского — транслитерация в общее внутреннее
   представление с сохранением исходного варианта в метаданных;
5. удаление служебных колонтитулов и разрывов страниц, мешающих разбору структуры.

### 2.3 Разбор структуры (`structure.py`)

Из текста выделяется иерархия «глава → статья → часть → пункт». Каждый структурный
элемент получает идентификатор вида `<doc_id>/<путь>`. Идентификатор строится по пути, а
не по счётчику — при повторной сборке корпуса идентификаторы не должны меняться, иначе
граф и индексы разойдутся.

### 2.4 Нарезка на фрагменты (`chunker.py`)

Правило одно и оно жёсткое:

> **Фрагмент не пересекает границу статьи или пункта.** Короткая статья даёт один
> фрагмент. Объёмная делится по абзацам. Перекрытий между фрагментами нет.

Почему так, а не скользящим окном фиксированной длины: ссылка в ответе должна указывать
на статью целиком или на её часть, а фрагмент, пересекающий границу, такую ссылку
сделать не позволяет. Отсутствие перекрытий убирает дубли из контекста и делает метрики
на множествах фрагментов корректными.

```python
def chunk_document(doc: Document, max_tokens: int) -> list[Chunk]:
    out = []
    for node in doc.leaf_nodes():           # статьи и пункты
        if count_tokens(node.text) <= max_tokens:
            out.append(Chunk(node, par=1, text=node.text))
        else:
            for i, par in enumerate(split_paragraphs(node.text), start=1):
                out.append(Chunk(node, par=i, text=par))
    return out
```

### 2.5 Эмбеддинги (`embed.py`)

Один и тот же кодировщик применяется к трём объектам: к фрагментам, к текстовым атрибутам
вершин графа и к запросу. Модель — многоязычная, размерность выхода **768**, дообучена на
параллельном русско-узбекском корпусе юридических текстов.

Важно для последующего обучения: **на фазе обучения с подкреплением кодировщик
замораживается**. Если менять его одновременно с политикой, признаки фрагментов
«поплывут» и контроллер будет учиться на подвижной основе.

### 2.6 Индексы

| Индекс | Назначение | Что кладём |
|---|---|---|
| Инвертированный | точные формулировки, номера статей | лемматизированные токены фрагментов |
| Векторный (ANN) | смысловая близость, синонимия, многоязычность | эмбеддинги фрагментов |
| Графовый | связи между нормами | вершины и типизированные рёбра |

Лемматизация выполняется с учётом морфологии двух языков — это отдельный шаг, общий для
индексации и для обработки запроса.

**Проверка этапа.** Число фрагментов совпадает с числом, полученным прямым подсчётом по
структуре; каждый фрагмент имеет непустой `parent`; повторный запуск конвейера даёт те же
идентификаторы.

## 3. Этап 2. Граф знаний

### 3.1 Схема (`schema.py`)

**Четыре типа вершин:**

| Тип | Примеры |
|---|---|
| документ | закон, кодекс, подзаконный акт, регламент |
| структурный элемент | глава, статья, часть, пункт, подпункт |
| сущность предметной области | орган власти, должность, процедура, правовая категория |
| юридическое понятие | термин, определение, правовая конструкция |

**Семь типов рёбер.** Шесть извлекаются из текста, одно вычисляется:

| Ребро | Как получено |
|---|---|
| содержит | из структуры документа |
| ссылается | по паттернам отсылок |
| уточняет / дополняет | по формулам изменения |
| отменяет | по формулам признания утратившим силу |
| регулирует | по упоминанию сущности в норме |
| определяет понятие | по конструкции определения |
| тематически связан | по косинусной близости фрагментов **разных** документов |

Схема должна быть данными, а не кодом: список типов и шаблонов лежит в `graph.yaml`,
`schema.py` только валидирует. Тогда подключение документов иной категории не требует
правки модулей извлечения.

### 3.2 Алгоритм построения (`build.py`)

Три вложенных цикла, каждый со своим условием:

```
V ← ∅;  E ← ∅

# Цикл 1 — по документам корпуса
для каждого документа d:
    выделить структурные элементы → вершины + рёбра «содержит»
    нарезать на фрагменты, посчитать эмбеддинги, задать μ
    извлечь сущности и понятия (правила + NLP-модель) → вершины

# по всему корпусу: явные ссылки
построить рёбра «ссылается» по паттернам отсылок

# Цикл 2 — по парам фрагментов разных документов
для каждой пары (c_i, c_j) из разных документов:
    если cos(e_i, e_j) > θ_sim:
        добавить ребро «тематически связан» с весом близости

# Цикл 3 — по нормам (статьям и пунктам)
для каждой нормы s:
    если s упоминает сущность или определяет понятие:
        добавить рёбра «регулирует» / «определяет понятие»
    если в тексте s есть формула изменения или отмены:
        добавить рёбра «уточняет/дополняет» / «отменяет» с датой

# завершение
разрешить дубли сущностей, проверить типы рёбер
присоединить изолированные вершины к ближайшим тематическим кластерам
сформировать признаки X;  E = объединение всех типов
вернуть G = (V, E, X)
```

Замечания по реализации:

- **Второй цикл — квадратичный.** В лоб пары перебирать нельзя. Практический путь: сначала
  ANN-поиск ближайших соседей для каждого фрагмента, затем проверка порога только среди
  кандидатов. Ограничение «разных документов» ставится фильтром до расчёта близости.
- **Ребро «отменяет» несёт дату.** Отменённая норма из графа не удаляется: запрос может
  касаться редакции на определённую дату. Хранится связь и дата вступления в силу.
- **Дедупликация сущностей** делается по нормализованному имени плюс тип; при слиянии
  рёбра переносятся на выжившую вершину.

### 3.3 Отображение μ

`μ: фрагмент → вершина` и обратное `μ⁻¹: вершина → множество фрагментов`. Контроллер
принимает решения на уровне **вершин**, а в контекст попадают **фрагменты**. Это
отображение — центральная структура данных, через неё связаны три уровня поиска.

### 3.4 Валидация графа

Автоматические проверки после сборки:

- нет вершин без типа и рёбер без типа;
- нет изолированных вершин (после этапа присоединения к кластерам);
- каждое ребро «содержит» ведёт от документа или элемента к его непосредственному потомку;
- у каждого ребра «отменяет» заполнена дата;
- каждая вершина-структурный элемент имеет хотя бы один фрагмент в `μ⁻¹`;
- доля латентных рёбер от общего числа не превышает заданного в конфиге предела —
  иначе порог `θ_sim` занижен и граф зарастает слабыми связями.

## 4. Этап 3. Три уровня извлечения

### 4.1 Лексический (`lexical.py`)

Полнотекстовый поиск с ранжированием BM25 поверх инвертированного индекса. Обслуживает
запросы с точными формулировками, номерами статей и наименованиями органов.

### 4.2 Векторный (`vector.py`)

ANN-поиск ближайших соседей по косинусной метрике. Обслуживает случаи, когда лексического
совпадения нет, а смысл тот же — в том числе при переходе между языками.

### 4.3 Графовый (`graph_walk.py`)

Обход графа по рёбрам заданного типа от уже покрытых вершин. Упорядочивание кандидатов —
персонализированным PageRank либо приростом информативности (см. 5.3).

### 4.4 Стартовая точка

```
V₀ = { v ∈ V : лексическая близость(q, v) > τ_lex
              ИЛИ смысловая близость(q, v) > τ_sem }

C₀ = ∅          # контекст пуст
F₁ = V₀         # опорные вершины образуют начальный фронтир
```

Дизъюнкция обязательна: точная формулировка ловится лексикой, пересказ своими словами —
вектором.

**Опорные вершины идут во фронтир, а не в контекст.** Переход монотонен — контекст только
растёт. Если положить фрагменты всех опорных вершин сразу в `C₀`, политика лишится
возможности от них отказаться, а именно отказ от избыточных кандидатов и составляет
содержание обучаемой стратегии.

## 5. Этап 4. Среда: марковский процесс

### 5.1 Формализация (`mdp.py`)

```
s_t = (q, C_t, G)              состояние среды
a_t ∈ A                        действие
C_{t+1} = C_t ∪ ΔC_t           монотонный переход
R                              начисляется только в терминальном состоянии
γ = 1                          дисконтирование не нужно, горизонт конечен
```

**Пространство действий.** Действие — это оператор извлечения, а не конкретный запрос к
БД:

| Оператор | Параметры |
|---|---|
| `lexical_search` | число возвращаемых фрагментов `k` |
| `vector_search` | число возвращаемых фрагментов `k` |
| `graph_traversal` | тип ребра `r`, число отбираемых вершин `m` |
| `STOP` | — |

Исполнитель (`executor.py`) транслирует оператор в последовательность конкретных вызовов
к хранилищам: `find_seed_nodes → traverse_graph → rank_nodes`. Такое разделение даёт две
вещи: политика работает с небольшим дискретным пространством действий, а синтаксическая
корректность обращений к БД гарантируется исполнителем, а не моделью.

### 5.2 Лимиты

Эпизод завершается при достижении любого из ограничений:

| Лимит | Смысл |
|---|---|
| `T_max = 10` | число шагов |
| `K_max` | число фрагментов в контексте |
| `L_max` | суммарная длина контекста |

Ограничения **конструктивные**, а не выученные: расход ресурсов ограничен сверху
независимо от того, чему научилась политика.

### 5.3 Правило ранжирования внутри оператора

Внутри графового действия вершины упорядочиваются по приросту информативности
`Δ_V(v | C_t)` и берутся `m` лучших. **Это правило детерминированное и обучению не
подлежит.** Обучаются: выбор уровня, тип ребра, значения `k` и `m`, момент остановки.

Разделение важно для отладки: если контекст собран плохо, сначала проверяется политика, а
не правило ранжирования.

## 6. Этап 5. Контроллер

### 6.1 Поток вычислений

```
текст вершины ──► кодировщик ──► h⁰ (768)
                                   │
запрос ──► кодировщик ──► e_q (768)┤
                                   ▼
                              GAT, 3 слоя ──► z_v (256)
                                   │
                      ┌────────────┴────────────┐
                пулинг по фронтиру        пулинг по контексту
                      f_t                        g_t
                      └────────────┬────────────┘
                        [ e_q ‖ f_t ‖ g_t ] ──► MLP политики ──► softmax по действиям
```

### 6.2 Графовая сеть (`gnn.py`)

```
h_v^(l+1) = σ( W₀·h_v^(l) + Σ_{u∈N(v)} α_uv · W₁·h_u^(l) + W₂·e_q )
```

Разбор по слагаемым:

- `W₀·h_v` — собственное содержание вершины не теряется при пересчёте;
- `Σ α_uv · W₁·h_u` — соседи подмешиваются с обучаемыми весами внимания, `Σα = 1`;
- `W₂·e_q` — **запрос входит в каждый слой**, поэтому представление вершины зависит от
  того, что спрашивают;
- `σ` — нелинейность, без неё слои схлопнулись бы в одно линейное преобразование.

Параметры: **3 слоя**, **8 голов внимания**, ширина слоя **256**. Голов восемь — это
восемь независимых взглядов на соседей, каждый со своими `α` и своими матрицами. Ширина
делится между ними: 256 / 8 = **32 на голову**, результаты конкатенируются обратно в 256.

Почему внимание, а не усреднение соседей: семь типов связей неравнозначны — переход по
«отменяет» несёт больше, чем по «тематически связан». Внимание позволяет сети выучить эту
разницу без ручной расстановки весов по типам.

Почему три слоя: глубина равна радиусу обзора в переходах. Цепочка «статья → отменяющий
акт → его элемент» укладывается в три. Дальше начинается переусреднение — представления
разных вершин сближаются. Недостающая глубина добирается не слоями, а шагами эпизода.

### 6.3 Агрегация состояния (`state.py`)

```
g_t = Pool({ z_v : v ∈ S_t })      # S_t — вершины, покрытые контекстом
f_t = Pool({ z_v : v ∈ F_t })      # F_t — фронтир кандидатов
```

`Pool` — усреднение; размерность сохраняется. В реализации агрегатор состояния дополнен
MLP на **128** единиц.

Смысл пулинга — **снять зависимость от размера**: фрагментов может быть три или тридцать,
во фронтире пять вершин или двести, а на вход MLP приходит вектор постоянной длины.
Усреднение также не зависит от порядка, что верно по существу: контекст — множество, а не
последовательность.

На первом шаге контекст пуст, поэтому `g₁` — нулевой вектор.

### 6.4 Политика (`policy.py`)

MLP с двумя скрытыми слоями **512 → 256** и softmax по действиям.

### 6.5 Что считается один раз, а что на каждом шаге

| Один раз на запрос | На каждом шаге |
|---|---|
| `e_q` | пулинг `g_t` и `f_t` |
| прогон GAT, все `z_v` | прямой проход политики |
| стартовый фронтир `V₀` | обновление фронтира |

Тяжёлая часть — GNN — отрабатывает однократно. Внутри эпизода крутится только лёгкая, за
счёт этого шаг укладывается в доли секунды.

### 6.6 Что контроллер НЕ видит

Тексты. Только векторы. Внешняя языковая модель в контуре отбора не вызывается ни при
обучении, ни в эксплуатации.

## 7. Этап 6. Функция вознаграждения

### 7.1 Состав (`reward.py`)

```
R(q, C, C*) = α·R_chunks + β·R_coverage + γ·R_diversity + δ·R_coherence
```

| Компонента | Формула | Что измеряет |
|---|---|---|
| `R_chunks(C, C*)` | F1 по множествам: `Prec = |C ∩ C*| / |C|`, `Rec = |C ∩ C*| / |C*|` | точность и полноту отбора |
| `R_coverage(C, G, q)` | `|Covered(C,G) ∩ Relevant(q,G)| / |Relevant(q,G)|` | покрытие релевантных зон графа |
| `R_diversity(C, G)` | `(1/ln H)·Σ_h (−p_h·ln p_h)`, где `p_h` — доля фрагментов на глубине `h` | разнообразие по глубине обхода |
| `R_coherence(C, G)` | `|LargestCC(C,G)| / |Nodes(C,G)|` | связность итогового подграфа |

Веса по умолчанию: `α = 0,5`, `β = 0,2`, `γ = 0,2`, `δ = 0,1`.

Разнообразие измеряется **энтропией распределения по уровням глубины**, а не разбросом
эмбеддингов: цель — заставить политику уходить от опорных вершин вглубь графа, а не
набирать формально непохожие фрагменты.

### 7.2 Почему награда на уровне фрагментов, а не по тексту ответа

Три следствия для кода:

1. генератор не участвует в обучении — цикл обучения не зависит от внешнего API;
2. если политика отобрала все эталонные фрагменты, а ответ плох, проблема однозначно
   локализуется в генераторе;
3. награду можно считать детерминированно и воспроизводимо.

### 7.3 Калибровка весов (`calibrate.py`)

Веса не назначаются на глаз:

```
λ* = (α, β, γ, δ) = argmax Corr( R_λ , M_eval )
```

на отложенном валидационном наборе, где `M_eval` — итоговая метрика качества. Корреляция
— Пирсона либо Спирмена; альтернативно задача решается линейной регрессией.

Полезное свойство при отладке: групповая нормализация преимуществ в GRPO инвариантна к
аффинному преобразованию награды, поэтому общий масштаб весов на обучение не влияет —
значима только их относительная пропорция.

## 8. Этап 7. Обучение

### 8.1 Данные для обучения

Каждая обучающая пара содержит:

```json
{
  "q": "...",
  "y_ref":  { "text": "...", "sources": ["<акт>, ст. N ч. M"] },
  "C_ref":  ["<chunk_id>", "..."],
  "trajectory": [
    { "t": 1, "op": "lexical", "arg": "..." },
    { "t": 2, "op": "graph",   "arg": "ссылается" },
    { "t": 3, "op": "stop" }
  ]
}
```

Поле `trajectory` — экспертная последовательность операторов. Именно её наличие делает
возможной первую фазу обучения.

### 8.2 Фаза 1 — обучение по экспертным траекториям

Прямое применение RL к случайно инициализированной политике непрактично: большинство
траекторий бессмысленны, награды около нуля, дисперсия градиентов велика. Поэтому сначала
политика обучается воспроизводить размеченные траектории обычной супервизией.

Результат фазы замораживается как **референсная политика** `π_ref` — она понадобится для
KL-регуляризации.

### 8.3 Фаза 2 — групповая оптимизация политики

```
J(θ) = E[ R(q, C_T, C*) ] − β_KL · D_KL( π_θ ‖ π_ref )
```

Схема шага:

1. на запрос порождается **группа из `G_s = 4` траекторий**;
2. для каждой считается награда `r_i` по отобранным фрагментам;
3. считается преимущество внутри группы: `A_i = (r_i − r̄) / (σ_r + ε)`;
4. делается шаг оптимизации с KL-штрафом к `π_ref`.

Группа нужна именно для шага 3: без нескольких траекторий на один запрос преимущество не
с чем сравнивать.

### 8.4 Гиперпараметры

| Параметр | Значение |
|---|---|
| траекторий на запрос `G_s` | 4 |
| скорость обучения | 3·10⁻⁴, Adam |
| коэффициент KL-регуляризации `β_KL` | 0,01 |
| максимальная длина эпизода `T_max` | 10 |
| кодировщик на фазе 2 | заморожен |

### 8.5 Цикл обучения (`loop.py`)

```
инициализация: SFT → π_ref ← π_θ,  R* ← −∞

для каждой эпохи:
    для каждой обучающей пары (q, C*):
        e_q ← encode(q)
        z ← GNN(G, e_q)               # один прогон на запрос
        F₁ ← V₀(q)

        для каждой попытки i = 1..G_s:
            C ← ∅;  F ← F₁;  H ← ∅;  t ← 1
            пока t ≤ T_max и |C| < K_max и len(C) < L_max:
                a_t ~ π_θ(· | s̃_t)
                если a_t = STOP: выйти
                выполнить оператор, обновить C, F, H, t
            r_i ← R(q, C, C*)          # без вызова генератора

        A_i ← (r_i − r̄) / (σ_r + ε)
        шаг GRPO с KL-штрафом

    оценить π_θ на валидации
    если награда > R*:  θ* ← θ;  R* ← награда

вернуть π_θ*
```

Обратите внимание на порядок: `GNN` считается **снаружи** цикла по попыткам — все четыре
траектории используют одни и те же `z_v`.

### 8.6 Что логировать

Без этого отладка RL невозможна:

- кривая функции потерь фазы 1;
- кривая средней награды по эпохам и её разброс внутри группы;
- распределение длин эпизодов — если все эпизоды упираются в `T_max`, политика не
  научилась останавливаться;
- распределение выбранных операторов — вырождение в один оператор означает коллапс
  политики;
- доля эпизодов, завершённых по `STOP`, а не по лимиту;
- значение KL к `π_ref` — рост означает, что политика ушла слишком далеко.

### 8.7 Типичные отказы и их признаки

| Симптом | Вероятная причина |
|---|---|
| награда растёт, качество ответов нет | «взлом награды»: политика концентрируется на узкой области графа — проверить вклад компонент покрытия и связности |
| эпизоды всегда максимальной длины | правило остановки не выучено, слишком мал штраф за длину |
| политика выбирает один оператор | коллапс, слишком большой шаг обучения либо слабая KL-регуляризация |
| награда шумит от эпохи к эпохе | мала группа `G_s`, преимущество оценивается ненадёжно |

## 9. Этап 8. Валидация

### 9.1 Разбиение данных

Прикладной корпус делится на три части с разными ролями:

| Выборка | Роль |
|---|---|
| обучающая | фазы 1 и 2 |
| валидационная | калибровка весов награды, подбор гиперпараметров, отбор лучшей эпохи |
| тестовая | итоговая оценка, в обучении не участвует |

Отдельно берутся общедоступные многопереходные QA-наборы: часть как in-domain (обучение и
тест), один набор целиком отложен как out-of-domain — проверка обобщающей способности без
дообучения.

**Правило, которое легко нарушить:** веса награды калибруются на валидации, а не на тесте.
Иначе тестовая оценка перестаёт быть честной.

### 9.2 Метрики (`metrics.py`)

Две группы: качество ответа и обоснованность ответа контекстом.

| Метрика | Что считает |
|---|---|
| **F1** на уровне токенов | совпадение с эталонным ответом; штрафует иные формулировки |
| **ACC_L** | точность по схеме «языковая модель как судья»: классификация ответа как корректного с учётом контекста, затем доля корректных |
| **SBERT** | семантическая близость ответа к эталону |
| **RA** | точность ссылок: `RA = (1/|Q|)·Σ_q |Ref(ŷ) ∩ Ref*| / max(|Ref(ŷ)|, 1)` — макро-среднее по запросам |

`RA` — ключевая для правового домена: ответ без верной ссылки на акт практически
бесполезен. Расхождение между `F1` и `ACC_L` — нормальное явление: токенная мера
чувствительна к формулировке, судья учитывает содержательную корректность.

При реализации `ACC_L` зафиксировать в конфиге: какая модель выступает судьёй, шаблон
промпта, порог бинаризации. Иначе результат невоспроизводим.

### 9.3 Базовые модели (`baselines.py`)

Сравнение выстраивается по двум осям — представление знаний и способ управления отбором:

| Класс | Представитель | Что показывает |
|---|---|---|
| без извлечения | языковая модель на параметрических знаниях | нижняя граница |
| одношаговое лексическое | BM25 + генерация | вклад точного совпадения |
| одношаговое векторное | ANN + генерация | вклад смысловой близости |
| графовое с эвристикой | обход графа по фиксированным правилам | вклад графа без обучения |
| обучаемое без графа | RL над плоским набором фрагментов | вклад обучения без графа |

Предлагаемый метод занимает свободную клетку: граф **и** обучаемая политика.

### 9.4 Протокол прогона (`runner.py`)

Единый для всех моделей, иначе сравнение некорректно:

1. одна и та же обучающая выборка;
2. один и тот же тестовый набор;
3. одинаковый ресурсный бюджет `L_max`, `K_max`, `T_max`;
4. один и тот же генератор для всех методов, использующих генерацию;
5. фиксированные зерна генератора случайных чисел, логирование версий моделей.

### 9.5 Абляции (`ablation.py`)

Из полной схемы поочерёдно исключается один элемент при неизменном бюджете:

| Вариант | Что проверяет |
|---|---|
| без обучения с подкреплением (только фаза 1) | вклад обучаемого управления |
| без графового уровня | вклад графа |
| без лексического уровня | вклад точного совпадения |
| без GNN-кодировщика (усреднённые признаки вместо топологии) | вклад именно графовых представлений, а не факта наличия графа |
| упрощённая награда (только `R_chunks`) | вклад составной награды |

Последний вариант оценивается иначе остальных: смена награды меняет цель оптимизации,
поэтому сравнивать итоговые метрики некорректно — наблюдаются устойчивость обучения и
распределение отобранных фрагментов по графу.

### 9.6 Проверки инженерного уровня

Помимо метрик качества стоит закрыть тестами:

- **детерминированность конвейера данных**: повторный запуск даёт побайтово те же
  фрагменты и идентификаторы;
- **согласованность хранилищ**: для случайной выборки фрагментов их наличие во всех трёх
  индексах и совпадение `parent` с вершиной графа;
- **соблюдение лимитов**: ни один эпизод не превышает `T_max`, `K_max`, `L_max`;
- **монотонность перехода**: `C_t ⊆ C_{t+1}` на всех шагах;
- **корректность μ**: каждый фрагмент из контекста принадлежит вершине, реально покрытой
  траекторией;
- **воспроизводимость обучения**: два прогона с одним зерном дают совпадающие кривые.

## 10. Этап 9. Система

### 10.1 Уровни

| Уровень | Задачи |
|---|---|
| представления | диалоговый интерфейс, отображение ответа со ссылками, панель использованного контекста |
| прикладной логики | маршрутизация, сессии, аутентификация и права, очереди, журналирование |
| интеллектуальной обработки | три ретривера, контроллер отбора, модуль генерации |
| данных | документы, метаданные, векторные представления, граф знаний |

Взаимодействие только через унифицированные интерфейсы: уровень представления общается с
сервером по REST для запросов и по WebSocket для уведомлений о ходе обработки.

### 10.2 Согласованность хранилищ

Один документ живёт одновременно в четырёх хранилищах. При обновлении документа
изменения расходятся событиями через брокер: пересчитываются фрагменты, эмбеддинги,
индексы и затронутые вершины графа. В коде это означает, что **точка входа на обновление
одна** — прямая запись в отдельное хранилище мимо события запрещена, иначе индексы
разойдутся с графом.

### 10.3 Сквозной поток запроса (`pipeline.py`)

```
запрос → шлюз (аутентификация, права) → очередь
       → кодирование запроса, прогон GNN, стартовый фронтир
       → цикл отбора под управлением политики
       → фильтрация фрагментов по уровню доступа
       → сборка промпта → генератор → ответ со ссылками
       → журналирование: запрос, результаты ретриверов, ответ, оценка пользователя
```

### 10.4 Безопасность

Во внешнюю модель уходит только отобранный контроллером набор фрагментов, прошедший
фильтрацию по категории распространения, и обезличенная формулировка запроса —
идентификаторы пользователя, сессии и подразделения исключаются. Объём передаваемого
минимизирует сам метод: контроллер отбирает ограниченное число фрагментов вместо передачи
документов целиком.

Архитектура допускает замену внешней модели на локально развёрнутую без изменения
остальных компонентов: политика обучена независимо от генератора и при его замене
переобучения не требует.

## 11. Порядок реализации

Каждый шаг закрывается своим критерием готовности — не переходить дальше, пока не закрыт.

| № | Шаг | Готово, когда |
|---|---|---|
| 1 | Конвейер данных: ingest → normalize → structure → chunker | повторный запуск даёт те же идентификаторы, у всех фрагментов есть `parent` |
| 2 | Эмбеддинги и три индекса | случайный фрагмент находится всеми тремя способами |
| 3 | Сборка графа, валидация схемы | проходят все проверки п. 3.4 |
| 4 | Ретриверы и исполнитель операторов | каждый оператор возвращает корректный результат на ручных примерах |
| 5 | Среда MDP с лимитами | случайная политика отрабатывает эпизоды без выхода за лимиты |
| 6 | Функция награды | на размеченной паре `R` растёт при добавлении эталонных фрагментов |
| 7 | Модель: кодировщик, GAT, пулинг, политика | прямой проход даёт распределение по действиям нужной размерности |
| 8 | Фаза 1: обучение по траекториям | политика воспроизводит экспертные траектории на обучающей выборке |
| 9 | Калибровка весов награды на валидации | найденные веса дают наибольшую корреляцию с итоговой метрикой |
| 10 | Фаза 2: групповая оптимизация | награда на валидации растёт, эпизоды завершаются по `STOP`, а не по лимиту |
| 11 | Оценочный стенд: метрики, базовые модели, протокол | все модели прогоняются одним скриптом при одинаковом бюджете |
| 12 | Абляции | каждый вариант отличается от полной схемы ровно одним элементом |
| 13 | Сборка системы: API, уровни, согласованность хранилищ | сквозной запрос проходит от интерфейса до ответа со ссылками |

## 12. Что важно не потерять при реализации

Короткий список решений, каждое из которых легко нарушить, а последствия проявятся поздно:

1. **Фрагмент не пересекает границу статьи или пункта.** Иначе ссылка в ответе теряет
   адресность.
2. **Опорные вершины — во фронтир, не в контекст.** Иначе политика не может отказаться от
   лишнего.
3. **Награда считается по фрагментам, генератор в обучении не участвует.** Иначе обучение
   становится дорогим и зависимым от внешней модели.
4. **Кодировщик заморожен на фазе обучения с подкреплением.** Иначе контроллер учится на
   подвижной основе.
5. **Запрос подмешивается в каждый слой GNN.** Иначе представления вершин перестают
   зависеть от вопроса.
6. **GNN считается один раз на запрос, а не на каждом шаге.** Иначе шаг перестаёт
   укладываться в бюджет времени.
7. **Веса награды калибруются на валидации, не на тесте.**
8. **Лимиты эпизода конструктивные, а не выученные.** Расход ресурсов должен быть
   ограничен сверху при любом поведении политики.
9. **Правило ранжирования внутри оператора детерминированное.** Обучается выбор действия,
   а не порядок кандидатов.
10. **Обновление документа идёт одной точкой входа через события.** Иначе индексы
    расходятся с графом.
